# F41 — Landscapes from Floe, kept up to date

**Status:** built 2026-11-02 (CHANGELOG). David's decisions, 2026-11-02: all five as proposed
(see the end). It builds on the Floe connection preset (F33, `src/presets.ts`), the Architecture
starter types and the import that adds them (2026-11-01), and `scripts/floe-diagrams.ts`.

**As built:** `src/floeMerge.ts` (what's Floe's and what's yours; pure, tested in
`test/floeMerge.test.ts`), `src/floeLandscape.ts` (preview, bring in, update, status, diagram
refresh), `src/floeDiagrams.ts` (diagram blocks, shared with the browser and the script),
`web/lib/floe.ts` (the commands' dialogs), and the end-to-end test "A landscape from Floe (F41)".
Differences from the design below:

- The end marker carries a short hash of Floe's part as written (`<!-- /floe 3f2a9c1b -->`), so
  the next update knows whether the person changed it, without storing anything outside the note.
- Each note also gets `floe-landscape: <id>` (one of Floe's keys), so a note moved out of the
  folder is still found, and removals are scoped to the landscape.
- Diagrams: per-block Update and Open in Floe buttons became note-level commands: **Update Floe
  diagrams** (⋯, when the note has a `%% floe:` block) and **Open in Floe** (⋯, on a landscape's
  notes, opening the landscape). Per-block buttons would mean a widget on every Mermaid diagram.
- Out of date: the overview's `floe-hash` covers the notes export, one request. A change only to
  a diagram shows up at the next Update, not in the "Floe has changed" message.
- A note moved within the landscape's folder is moved back to Floe's place on update; one moved
  out of the folder stays where it is, with Floe's name.
- The "From Floe" label is drawn in Live Preview only; read mode hides the markers already.

## Why

Floe holds the model; Skein is where the thinking about it goes: why a system is shaped as it
is, what was decided in the meeting, what to watch. Today a landscape comes in as Floe's
folder-of-notes zip, and keeping it current is where it breaks:

| Today | What goes wrong |
|---|---|
| Export in Floe, download, import here | Two apps, a file in between, every time |
| Re-import with **overwrite** | Each note is replaced whole: **anything you wrote in it is lost** |
| Re-import with **keep both** | A second copy of every note |
| An object renamed in Floe | Comes in as a new note; the old one, with your writing, is left behind |
| An object removed in Floe | Its note stays, with nothing saying it's gone |

The point of having the landscape here is to write beside it, and today updating it undoes that.

## In a sentence

⌘K → **Bring in a landscape from Floe…** puts a landscape into a folder, and later **Update from
Floe** changes only what Floe owns in each note, matched by `floe-id`, so your writing survives;
renames follow, and removed objects are marked, never deleted.

## Who owns what

The whole design rests on one rule: **every part of a brought-in note belongs either to Floe or
to you, and an update only ever touches Floe's.**

```markdown
---
type: system                 ← Floe's (a fixed list of keys, below)
technologies: [Node.js]      ← Floe's
floe-id: 3f2a…               ← Floe's: how the note is found again
reviewed: 2026-10-30         ← yours: any key Floe doesn't write
---
<!-- floe -->
Takes card payments.         ← Floe's: everything Floe's export writes in the body
## Uses
- → [[Stripe]] charges cards
<!-- /floe -->

## Why it's shaped like this   ← yours: everything outside the markers
…
```

- **Floe's keys** are the ones its export writes: `type`, `technologies`, `tags`, `owner`,
  `status`, `external`, `classification`, `personal-data`, `payment-data`, `criticality`,
  `part-of`, `floe-id`. An update sets them as Floe has them now, and removes one Floe no longer
  writes (Floe leaves out `status: live` and `external: false`). Every other key is yours and
  is kept, in its place.
- **Floe's region** is the body between `<!-- floe -->` and `<!-- /floe -->`. An update replaces
  it whole. Everything outside it is yours.
- **Your edits inside Floe's part** are overwritten by the next update, and the preview says so
  before it happens (see Decision 1). The region shows a quiet label, "From Floe · updated
  3 Nov", so this isn't a surprise.
- **Plain Markdown throughout**: the markers are HTML comments, so an export opens in any editor
  and Obsidian hides them. Nothing about a landscape is stored outside its notes (the CLAUDE.md
  rule for types).

## Where the data comes from

Floe's own exporter, not a copy of it. `GET /api/landscapes/:id/export?format=notes` returns the
same zip as **⋯ → Export as folder of notes**, with the same bearer token as Floe's MCP server
(radar-scout uses both). So:

- The REST address comes from the connection's MCP address (`…/mcp` → `…/api`), and the request
  goes through `src/egress.ts` like every other request to an address a person gave.
- Each file in the zip is entirely Floe's: its frontmatter is Floe's keys, its body becomes the
  region. Skein never re-implements Floe's format, so a Floe change to its export needs no change
  here, and nothing needs changing in Floe.
- Floe's MCP server has no tool for the zip. Adding one would mean a change in Floe, so REST it is.

## The flows

### 1. Bring in

⌘K → **Bring in a landscape from Floe…** (needs a Floe connection; otherwise the command offers
to connect one). Choose the landscape (from `floe_landscapes`), and a folder (default
`Architecture/<landscape>`). The dialog says what will happen ("42 notes, and the System, App and
Store types"). **Bring in**:

- runs `assertRoom` for the zip's expanded size (the storage guard), then creates each note with
  Floe's keys and the region, and adds missing starter types (the import's helper);
- writes the landscape's overview note with `floe-landscape: <id>`, `floe-updated: <date>`,
  and a **Diagrams** region holding a `%% floe:` block per diagram, filled.

### 2. Update from Floe

From the overview note's ⋯ menu, or ⌘K when the open note is in a brought-in folder. Like every
write here, it **previews first**:

> **Payments, from Floe:** 3 changed · 2 new · 1 renamed (Ledger → Payments ledger) ·
> 1 removed in Floe. Your writing in 12 notes is kept. Owner changed in **Payments API**, which
> you had edited: Floe's value wins.

**Update** applies it: each note through `overwriteContent` with a function, so it applies to the
live text and can't undo someone's typing; one revision per burst (reason `floe`), as automated
writers do. Notes are found by `floe-id` anywhere in the collection, not by path.

### 3. Renames and removals

- **Renamed in Floe:** the note is renamed with `renameNote` (which updates links to it), but
  only if it's still where the last update put it. If you moved it, it stays where you put it,
  and gets the new title.
- **Moved in Floe** (a new parent): as a rename, since the folder follows the containment.
- **Removed in Floe:** the note stays. Its `status` becomes `removed` and its region says
  "Removed from Floe on 3 Nov 2026". Your writing is untouched. Nothing deletes.
- **Notes you made in the folder** have no `floe-id`, so updates never touch them.

### 4. Diagrams in the app

The pure part of `scripts/floe-diagrams.ts` (finding, resolving and rewriting blocks) moves to
`src/floeDiagrams.ts`, shared by the server and the script:

- `/` menu → **Floe diagram…**: choose the landscape, then the diagram, and the block goes in
  filled. No names to type.
- A filled block shows **Update** and **Open in Floe** (`#/l/<landscape>/d/<diagram>`).
- Update from Floe refreshes the blocks in the brought-in folder too.

The script stays, for refreshing many notes from a terminal.

### 5. Knowing it's out of date

The overview note keeps `floe-hash`, a hash of the last zip. Opening it asks Floe for the zip
once (Decision 3), and if the hash differs, a quiet banner says "Floe has changed since 3 Nov ·
Update". Floe's webhooks could push this instead, but they would need an address Floe can reach
and a way to trust what arrives: not now.

## Safety

- **Nothing changes in Floe.** It's read with the connection's read-only token (F33 Decision 1).
  Everything F41 writes is the person's own notes, with a preview first.
- **What's sent to Floe** is a landscape id: no note text, so F33's send-out rule doesn't ask.
- **Personal landscapes only**, as with the connection itself: a work landscape doesn't belong in
  a personal library.
- **Size:** `assertRoom` before each bring-in and update, and the 5 MB note cap per note.
- **What comes back is data.** Floe's text goes into notes as Markdown through the same path as
  an import. It never reaches the assistant as instructions, and diagrams render in strict mode.

## Steps

1. **Bring in (S–M):** the command, the dialog, the REST fetch through egress, regions,
   types, the overview note with its Diagrams region.
2. **Update with a preview (M):** matching by `floe-id`, the key and region merge, the
   preview, revisions by burst.
3. **Renames and removals (S).**
4. **Diagrams in the app (S):** the shared module, the `/` menu entry, Update and Open in Floe
   on blocks.
5. **Out of date (S):** the hash and the banner.

**Done when** a person brings a landscape in from a connected Floe, writes in its notes, renames
an object and removes another in Floe, runs Update, and sees the preview list both; after
Update their writing is all there, the renamed note has kept its backlinks, the removed one is
marked `removed`, and the collection's export opens in Obsidian with the markers hidden.

## Checks before building

- **Live Preview and the markers.** Read mode hides HTML comments (`render.ts` sanitises them
  away), but Live Preview is CodeMirror. A marker line may show as text. If so, draw each
  marker as the quiet "From Floe" label (a widget, as callouts are).
- **`renameNote` and links** inside other people's writing: confirm it rewrites `[[Old]]`
  everywhere, including inside your parts, and leaves Floe's regions for the update to rewrite.
- **The token on REST:** confirm a read-only `flt_` token may call `/export` (radar-scout does
  with a read and edit token).

## Decisions (David, 2026-11-02: all as proposed)

1. **Your edits to Floe's part:** Floe wins, with the preview naming each one (proposed). Or the
   region is read-only in the editor (more work, and a surprise when typing).
2. **Is this within F33's read-only rule?** It reads Floe only, and writes only your notes, so
   proposed yes. Or keep it as a separate command outside Connections.
3. **When to check for changes:** when the overview note opens (proposed: one request), or once
   a day, or only when asked.
4. **The default folder:** `Architecture/<landscape>` (proposed), or the collection's root.
5. **One landscape, several collections:** allowed, each kept separately (proposed), or one
   collection per landscape.
